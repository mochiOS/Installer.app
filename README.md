# mochiOS Kinako Installer

Installer uses native AppCore/ViewKit components. Product UI is English. All
legal and disclosure bodies in this build are external UTF-8 placeholders whose
exact contents are `abcdef`, without a trailing newline. They are not legal
text authored by this implementation.

## Structure

- `documents.rs`: bounded external document/catalog loading. No `include_str!`
  legal text. License data is separate from UI and can be read after installation
  from the same bundle. The package installs `legal/` as application resources.
- `model.rs`: thirteen-page wizard, document acknowledgments, staged data
  choices, summary edits, final destructive confirmation, success/error state.
- `backend.rs` / `native.rs`: real inventory, activation guard and native adapter.
- `engine.rs`: revalidation, installation result checking, target-only consent
  persistence/read-back, then provider finalization. No UI state can skip this.
- `controller.rs`: bounded worker channel; no disk or service I/O during paint.
- `ui.rs`: native shared components, independently scrollable license panes,
  responsive footer, cached view trees, inline modal confirmations.

The three policy versions are independent of legal-document revisions and of
one another. Disclosures are keyed by category and locale in `legal/catalog.json`;
English is the UI default and locale fallback. No shared localization API was
found in AppCore; Settings currently owns its own language preference. This
implementation does not invent or replace an OS localization service. Actual
Japanese legal text must be supplied as versioned files later, not translated or
generated by this program. Example Library has no specified version; the UI says
so instead of inventing one. mochiOS's displayed version comes from the build.

## Native installation implementation (disabled)

The installation mechanics now live in Installer itself, in `deployment.rs` and
`target_data.rs`. AppCore contains only the generic `StorageRegion` Handle API.
No installation service, kernel installation policy, host block-device access or
fake completion path is introduced.

`native.rs::INSTALLATION_ENABLED` is deliberately **false**. Preparation and every
execution stage reject before acquiring writable storage authority. There is no
preference, CLI argument, environment variable or Cargo feature to turn it on.
Installer's manifest has not acquired `device.storage`,
`device.storage.scoped.write`, or a delegated filesystem control endpoint.
Installation sources are not added to the running image by this change. These
are intentional activation boundaries, not steps users should work around.

The dormant native path does the following:

1. Open a regular `disk.img` and exact-size `disk.manifest` from the read-only
   `/system/installation` resource directory. Pin the source file and validate its
   signature against the existing release public key, exact Installer release and
   build, architecture and full SHA-256. Development keys are never accepted by
   the shipped adapter.
2. Validate both GPT copies and tables, the existing seven-partition A/B layout,
   both signed Boot/System pairs, and initial redundant Boot State. Cached GPT
   metadata must equal the bytes covered by the source hash, including when the
   source changes between parsing and hashing.
3. Display the exact source partition sizes and destructive plan. Recheck the
   observed target and the hardware epoch retained in the reviewed plan before
   the first write, and acquire a filesystem-owned native
   region. The driver pins the actual device, checks its hardware epoch and range,
   excludes mounted disks and refuses ambiguous or unsupported hardware.
4. Generate new disk/partition GUIDs using the OS random API before any write.
   Invalidate old GPT metadata, copy the signed image body, flush, hash the source
   again and read back every copied byte. No success follows short or failed I/O.
5. Open only the target Data filesystem through the bounded region using the
   existing ext4plus implementation. Save device consent as root-owned mode 0600
   at `/var/config/privacy/consent.json`, reject unsafe directory/symlink layout
   and pre-existing receipts, flush and verify through a fresh filesystem reader.
   This never mounts over or writes into the running OS.
6. Reverify ESP, Boot A/System A, Boot B/System B and Boot State. Only then write,
   flush and read back the backup GPT, primary GPT and protective MBR. Report
   completion only after all stages succeed.

The accepted layout comes from the existing A/B image builder. The template's
filesystem sizes are preserved; a larger destination gets its backup GPT at the
physical end and remaining capacity is left unallocated. This does not invent a
new sizing policy, silently resize filesystems or promise secure erasure. Only
512-byte logical sectors are currently supported. The seven partitions are ESP,
Boot A, System A, Boot B, System B, Data and Boot State.

The source must be a clean distribution template, not a copy of the running
user's disk. A source build and its UEFI loader remain subject to the existing
release signing/Secure Boot pipeline. The new 256-byte deployment manifest has a
separate `mochios-install-image-v1` signature domain; it is an internal Installer
artifact introduced here, not a pre-existing OS disk format or legal document.
`image_manifest.rs` specifies its strict encoding.

### Preparing an offline installation source

The host-only `installer-image-sign` binary accepts:

```
installer-image-sign IMAGE MANIFEST RAW_PRIVATE_KEY VERSION BUILD EXPECTED_PUBLIC_KEY_HEX
```

Use a release-signed image from `scripts/mmake/build-ab-layout-image.sh`, the exact
release/build, and the public key already trusted by the native adapter. The key
must be a 32-byte raw private key; the expected public key is mandatory. The tool
creates a new manifest file, synchronizes it, and never opens a destination disk.
Ship the image as `disk.img` and manifest as `disk.manifest` in the separate
installer medium's `/system/installation` directory. Do not embed an image inside
itself or place the large source in initfs. No staging or launch grant is enabled
by this implementation.

### Verification and limits

Tests exercise the actual deployment implementation on temporary **regular
files** with GPT, signed slot fixtures and a real ext4 Data filesystem. The final
Data image is checked with `e2fsck -f -n`. Host tests require `sfdisk`, `mke2fs`,
`fakeroot`, and `e2fsck`; give `TMPDIR` enough space for concurrent image tests.
Tests cover invalid signatures/releases, source mutation, metadata binding,
insufficient capacity, entropy failure, write/read-back/flush errors, consent
persistence and refusal to finalize before settings are durable. Driver tests and
native builds cover the lower adapters separately.

These are not physical-machine installation, power-cut, UEFI boot or Secure Boot
qualification tests. The existing OS still exposes no supported application-level
restart API (Binder also reports restart unsupported); Installer keeps Restart
disabled and reports this limitation rather than claiming that reboot works.
A window-close request remains rejected during destructive installation.

## Consent and future consumers

Shared device records live in the standalone `mochios-device-consent` library;
AppCore contains no installer-specific consent API. See
`tools/devkit/docs/device-consent.md` for gate, persistence, withdrawal, queue and
update requirements. Installer state is in memory until a verified installation
has reached target persistence; it never writes consent into the running system.
AppStore terms are outside this wizard and must be handled at first AppStore use.

## Preview and build

`./scripts/dev/preview-app.sh installer run` supports the same Cargo patch options
as other apps. `mmake ui` includes Installer in the Linux desktop catalogue.
`mmake installer` remains the native target. Preview requires no login and never
obtains raw disk authority. UI and model tests cover all thirteen pages, consent
gates/edits, safe target selection, final confirmation, and failure paths.

## Optional data choices

The three independent pages are **Usage & Diagnostics**, **Crash Reports** and
**Update Results**. Each starts unselected. Agree/Disagree changes only the
in-memory draft; Continue commits the decision, timestamp and category-specific
policy version. Disagreement never blocks installation or OS updates. Back and
summary edits preserve the other choices and the legal-document receipts.

Each page loads its summary and all six expandable disclosure bodies from
external `abcdef` files. See `tools/devkit/docs/data-consent-contract.md` for the
AdminDashboard/client audit; no real privacy explanation is authored here.
Schema 2 does not reuse legacy category grants. No receipt is uploaded to the
dashboard. Settings UI and a new retention/re-consent queue remain out of scope.
