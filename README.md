# mochiOS Kinako Installer

Installer uses native AppCore/ViewKit components. Product UI is English. All
legal and disclosure bodies in this build are external UTF-8 placeholders whose
exact contents are `abcdef`, without a trailing newline. They are not legal
text authored by this implementation.

## Structure

- `documents.rs`: bounded external document/catalog loading. No `include_str!`
  legal text. License data is separate from UI and can be read after installation
  from the same bundle. The package installs `legal/` as application resources.
- `model.rs`: thirteen-page wizard, document acknowledgments, staged data
  choices, summary edits, final destructive confirmation, success/error state.
- `backend.rs`: real AppCore storage inventory and the native provider boundary.
- `engine.rs`: revalidation, installation result checking, target-only consent
  persistence/read-back, then provider finalization. No UI state can skip this.
- `controller.rs`: bounded worker channel; no disk or service I/O during paint.
- `ui.rs`: native shared components, independently scrollable license panes,
  responsive footer, cached view trees, inline modal confirmations.

The three policy versions are independent of legal-document revisions and of
one another. Disclosures are keyed by category and locale in `legal/catalog.json`;
English is the UI default and locale fallback. No shared localization API was
found in AppCore; Settings currently owns its own language preference. This
implementation does not invent or replace an OS localization service. Actual
Japanese legal text must be supplied as versioned files later, not translated or
generated by this program. Example Library has no specified version; the UI says
so instead of inventing one. mochiOS's displayed version comes from the build.

## Native support and remaining gaps

The former Installer was a four-page UI preview with fictitious disk data. That
preview data has been removed. Linux preview has no disk substitution: unsupported
inventory is reported as an error, and no host device is opened.

Existing storage inventory is read-only and capability checked. It provides
logical inventory IDs, not necessarily raw block-device IDs. Running-system,
boot and installation-source mappings, and all other mounted volumes are
protected. If any mounted volume cannot be mapped safely, the source, hardware
capacity, or writable status cannot be verified, a disk is not selectable.
Selection is cleared on every discovery refresh. Installation re-enumerates and
revalidates the exact target after the final confirmation, before any write.

**Fresh installation is not available in the existing native APIs.** The native
provider consequently refuses preparation/installation and cannot produce an
Installation Complete result. This is a real blocker, not a simulated success.
The UI permits reviewing the missing plan, but Install remains disabled.

Investigated implementations:

- AppCore `storage::inventory()` / filesystem inventory handle: real read-only
  enumeration, requiring `fs.read.all`.
- Core block operations: require `device.storage`. Inventory IDs must not be
  cast into block IDs. No capability or service-policy bypass is added.
- `STORAGE_CONTROL_INSTALL_PARTITION` is an ABI constant, not a documented
  complete fresh-install protocol. Guessed arguments are not sent to it.
- `services/update/src/installer.rs`: verifies signed updates and writes the
  inactive Boot/System pair in a pre-existing GPT A/B installation. It cannot
  create a fresh partition map, initialize Data, or install an ESP.
- `scripts/mmake/make-disk-image.sh`: host-only legacy ESP/System/Data builder.
- `scripts/mmake/build-ab-layout-image.sh`: host-only ESP, Boot A/System A,
  Boot B/System B, Data, Boot State image builder. Its development image sizes
  are not silently adopted as an installer sizing policy.
- `mboot/scripts/build-image.pl`: installer medium ESP plus payload, distinct
  from the installed A/B layout.

A supported native provisioner must supply an authoritative source identity,
signed source artifacts and target layout, target-specific destructive plan,
format/copy/progress operations, read-back verification, a verified mounted Data
root, and final boot configuration/flush. Only after that verified-target stage
can engine.rs publish device consent under the target's `var/config/privacy`.
A finalization error or persistence error prevents the completion screen.

No supported application-level restart API was found. Protocol/capability names
alone are not treated as working restart operations. The native provider reports
restart unsupported; the completion UI disables that action accordingly.

Tests use an explicitly test-only backend and temporary directories. No fake
backend, disk, progress timer, or success override exists in the shipped app.
A window-close request is rejected while destructive installation is running.

## Consent and future consumers

Shared device records live in AppCore `consent`. See
`tools/devkit/docs/device-consent.md` for gate, persistence, withdrawal, queue and
update requirements. Installer state is in memory until a verified installation
has reached target persistence; it never writes consent into the running system.
AppStore terms are outside this wizard and must be handled at first AppStore use.

## Preview and build

`./scripts/dev/preview-app.sh installer run` supports the same Cargo patch options
as other apps. `mmake ui` includes Installer in the Linux desktop catalogue.
`mmake installer` remains the native target. Preview requires no login and never
obtains raw disk authority. UI and model tests cover all thirteen pages, consent
gates/edits, safe target selection, final confirmation, and failure paths.
